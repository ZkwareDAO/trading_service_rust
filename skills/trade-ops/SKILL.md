# 交易助手

对接交易服务，解析用户自然语言指令并调用后端 REST API。

**重要说明**：
- **URL 的 base（host:port）从 `reference/config.yaml` 的 `api.base` 读取，禁止硬编码主机地址**
- **所有 API 调用使用 curl 命令执行**
- **给用户的响应必须使用表格形式展示数据**
  - 必须输出**标准 GFM 表格**，且表格**上方留一个空行**（紧贴正文会导致部分渲染器不识别）。
  - 表格必须**三行结构齐全**：① 表头行 → ② **分隔行**（每列对应一个 `---`，列数与表头相同，如 `|---|---|---|`）→ ③ 数据行。
  - 正确形态（注意表头前有空行、第二行是分隔行）：

    | 标的 | 方向 | 数量 |
    |------|------|------|
    | SOLUSDT | 空 | 0.84 |
  - 禁止只写「表头行 + 数据行」而漏掉 `|---|` 分隔行；分隔行缺失会退化成带竖线的裸文本、不被渲染成表格。所有列表/明细结果（仓位、订单、规则、账户）一律遵守。
  - **⚠️ 发送前强制自检（不可跳过）**：回复中每出现一个表格，发出前逐表核对——该表第 2 行是否为只含 `|`、`-`、`:`、空格的**分隔行**、且列数与表头一致？表格上方是否有空行？**任一项不满足，先补/改正后再发送**；不得把未通过自检的内容交给用户。
- 订单 / 仓位 / 规则 / 账户为**单一服务、同一端口**，统一使用一个 base（`api.base`）

## 2. 通用约定

### 2.0 解析严格度分层（最高优先级）

解析一条指令时，先判断意图（开仓 / 风控 / 查询 / 撤单），再按下列两层严格度取要素。

**① 语法严格、不允许二义 —— 数值与关键身份要素**

下列要素一旦出现含混、缺省导致两种以上解读、或无法对号入座，**必须停下来追问，禁止靠位置猜测**：

| 要素 | 严格规则 |
|------|----------|
| 价格 | 纯数字，限价/价格条件必填；无法判定是价格还是数量时追问 |
| 杠杆 | 必须带 `x` 后缀（`10x`）；不带 `x` 不得当杠杆 |
| 金额 | 必须带 `u` 后缀（`80u`）→ `order_cash`；不带 `u` 不得当金额 |
| 数量/百分比 | 裸数字=数量（币/张）；带 `%`=百分比（平仓/ROI 用），二者不可混 |
| 方向 | long/多/买、short/空/卖，必须唯一；看不出多空则追问 |
| 币种/标的 | 裸币种（btc）与完整合约名（`ETH-18SEP26-2550-P`）须能唯一确定；歧义追问 |

**② 允许模糊匹配 —— 让输入更友好**

| 要素 | 可接受写法（模糊） |
|------|--------------------|
| 交易所 | 币安：`B` / `binance` / `币安`；Deribit：`D` / `deribit`；Hyperliquid：`H` / `hyperliquid`（后端未接通时如实告知）；CTP 国内期货：`C` / `ctp` / `CTP`（**只认这三种写法**；单独的「期货」是币安形态的合约类型词位，不据此判 CTP） |
| 开仓动词（四个平级，按词面区分类型） | **`市价开仓`**（即时市价）/ `限价开仓`（即时限价）/ `市价条件开仓`（new 规则·market）/ `限价条件开仓`（new 规则·limit）；裸 `开仓` / `new` / `新开仓` / `建仓` 默认按**限价开仓** |
| 查询动词 | 仓位查询 = 仓位 = 仓位列表；风控查询 = 风控列表 = risk；止盈止损 = 风控 = risk = 止盈 = 止损 |

**开仓指令的硬约束**：开仓指令全文（含条件部分）**一旦出现「止盈 / 止损 / 止盈止损」字样，一律判为非法并提示**——到价平仓属于 risk 规则，不应出现在开仓里。需对已有持仓设保护时走风控指令。

### 2.1 请求

- `Content-Type: application/json`；POST/DELETE 带 JSON 体，GET 参数走 query（curl `-G --data-urlencode`）。
- 字段命名 `snake_case`；定点数（价格/数量/比率）传 JSON 数字或数字字符串皆可，**禁止**科学计数/浮点猜测。
- 列表响应：`data = { list:[...], total, page, page_size }`，**默认按 id 倒序（最新在前）**。
- 成功 `code=0`；非 0 见错误处理章节。

### 2.2 解析映射

**交易所（口语 → 线上精确名）**

| 输入 | 线上 `exchange` |
|------|-----------------|
| B / 币安 / binance | `binance` |
| D / deribit | `deribit` |
| H / hyperliquid | `hyperliquid`（服务端未接通时如实告知） |
| C / ctp / CTP | `ctp`（国内期货；**只识别 `C`、`ctp`、`CTP` 三种写法**，「期货/合约」不是交易所别名） |

> 仓位流水线实际接通 **binance U 本位永续（`instrument_type:"futures"`）、deribit 期权（`instrument_type:"option"`）与 CTP 国内期货（`exchange:"ctp"` + `instrument_type:"futures"`）**；其余类型以服务端支持为准，调用前可用账户/仓位接口确认。

**合约类型**

| 输入 | `instrument_type` |
|------|-------------------|
| 合约 / 永续 / U 本位 | `futures` |
| 国内期货（CTP） | `futures`（但**交易所必须显式为 `C/ctp/CTP`**；不能只凭「期货」二字判为 CTP） |
| 现货 | `spot` |
| 期权 | `option` |

**方向（口语 → 线上 `side`）**：多/买/long → `buy`；空/卖/short → `sell`。
**持仓方向出参**为大写 `BUY`/`SELL`，展示为「多/空」。

**杠杆与数量**

| 输入 | 字段 | 示例 |
|------|------|------|
| `{n}x` | `leverage=n` | `10x` → 10 |
| 直接给币/张数 | `quantity` | `0.1`（BTC 数量） |
| `{n}u`（投入金额） | `order_cash` | `1000u` → 1000（服务端换算数量） |

- 下单数量与金额**二选一**：
  - 直接给数量 → `quantity`（币/张数，如 `0.1`）；
  - 给下单金额（如 `1000u`）→ **`order_cash`**（**名义金额**，单位 U，即这张仓位的名义价值，**不是保证金**），由**服务端**按 `数量 = order_cash ÷ 参考价` 换算（限价用委托价、市价取可成交盘口/估值价）。**杠杆不参与换算、仅影响占用保证金**（保证金 ≈ 名义 ÷ 杠杆）。**agent 不自行换算**，把用户给的金额原样传入；换算结果落 `order_quantity`，`order_cash` 也随订单持久化。
- 用户给百分比 `{n}%` → 比率 `n/100`（`30%` → `0.3`）。**用户须输入百分比，不直接输入小数。**

> **CTP 数量铁律（仅 `ctp` 所，不影响其他所）**：
> - **只认正整数手数** → `quantity`（如 `2` = 2 手；1 手 = 1 张）；小数手数（`1.5`）、0、负数会被柜台前置拒绝。
> - **禁用金额（cash）形态**：CTP 指令里**绝不解析/发送 `{n}u`、`order_cash`**；用户若写「80u」，不换算、不猜测，直接追问让用户改报手数。
> - **没有杠杆词位**：CTP 不支持程序化设置杠杆（保证金率由柜台/交易所规定），指令中**不出现、不下发 `{n}x`/`leverage`**；误带杠杆时提示 CTP 无杠杆语义并请用户确认。
> - 上述约束只针对 CTP 形态；binance 的金额/杠杆、deribit 的张数解析规则保持原样。

**标的符号（口语 → 交易所原生 `instrument`）**

| 输入 | 币安合约 instrument | Deribit | CTP |
|------|---------------------|---------|-----|
| BTC / btc | `BTCUSDT` | 完整合约名 `BTC-27DEC26-100000-C` | —（CTP 无裸币种映射，须给完整合约号） |
| ETH / eth | `ETHUSDT` | 完整期权名 | — |
| CTP 合约号 | — | — | **原样透传**（大小写敏感，仅 trim），如 `rb2510`（螺纹）、`cu2512`（沪铜）、`IF2512`（股指） |

> 币安永续统一在符号后补 `USDT`；服务端也会按所做大小写归一（传 `btcusdt` 亦可，回显为大写）。
> **CTP 合约号不补后缀、不大写归一**：用户给什么（trim 后）就发什么；裸币种（btc/eth）不能推成 CTP 标的，须让用户报完整合约号。

### 2.3 止盈止损条件（watch_rule risk）

risk 规则请求固定带 `rule_type:"risk"` 与 **`position_id`**（从仓位查询拿），**不传 side/instrument**（服务端按 position_id 找仓位、平仓方向自动取反）；`exchange` 币安可省，deribit / **ctp** 等非默认所必须显式带。

| 条件 | `condition_kind` | `operator` | `value` | `condition_instrument` |
|------|------------------|-----------|---------|------------------------|
| ROI 止损 | `roi` | `<=` | 负比率，如 -0.3（止损 30%） | 留空 |
| ROI 止盈 | `roi` | `>=` | 正比率，如 0.6（止盈 60%） | 留空 |
| 价格涨过止盈 | `price` | `>=` | 绝对价格 | 留空=本仓位标的；跨标的填原生符号 |
| 价格跌破止损 | `price` | `<=` | 绝对价格 | 同上 |
| 关联仓位平仓 | `position` | `==` | `0` | **必填**关联标的原生符号，如 `ETHUSDT` |
| 盈利回落止盈 | `profit_drawdown` | `>=` | 回落比率，如 0.05 | 留空（连锁后继规则用） |

**平仓量二选一**：
- 按比例（最常用）：`quantity` 不传或 0，`quantity_pct` 给比率（全平 `1`、半仓 `0.5`）；
- 按绝对数量：`quantity` 给数量，`quantity_pct` 不传。
- 平仓单类型 `order_type`：市价 `market`（默认，止盈止损建议）/ 限价 `limit`（限价时另需 `price`）。
- `action`：默认 `self`（命中即执行本规则平仓）；只有回落止盈的**触发规则**用 `rule:<ref>`。

> **ROI 口径**：`roi` 条件现在按保证金收益率表示，具体处理由后端完成。止损 30% → `value:-0.3`，止盈 60% → `value:0.6`；用户口语「止损/止盈百分之几」直接 `n/100` 带符号填入即可。

### 2.4 条件提取（按位置 + 文字，不强制加 `== ==`）

**用户不会特意给条件加标记，因此一律从指令尾部自然语言中提取条件**，不要要求用户写成 `==…==`。`==…==` 仅作为**可选**的显式边界标记：出现时取标记内文本；不出现时按下述规则从尾部提取。

**提取位置**

| 指令 | 条件所在位置 |
|------|--------------|
| 条件开仓（市价/限价，binance / deribit / ctp） | 下单要素解析完后，**末尾剩余的整段文字**即条件（ctp 形态下单要素只取手数，见 2.2/3.2） |
| 风控 risk | 标的、`平仓量`（可选）解析完后，**最后部分的整段文字**即条件（`止损值…，止盈值…`、`回落止盈…`、`btc价格涨过…`、`关联仓位…` 等） |

**提取与切分规则**

1. 先按 2.2 / 3.2 从前部吃掉固定要素（交易所、现货合约、账户、标的、价格、方向、杠杆、金额、张数）与风控的可选 `平仓量`；**剩下未能对号入座的尾部文本整体作为条件候选**。
2. 尾部文本一旦命中下方词典的某个条件句式（含「价格涨过/跌破」「仓位大于/小于」「盈利/亏损/ROI」「回落」「关联仓位」「止损值/止盈值」），即确认为条件；**完全识别不出任何条件句式时，不要把它当地点/备注静默丢弃，应追问用户条件是什么**。
3. 条件以**标点（`，` `,` `；` `/`）切分**为多条独立条件：
   - 一段尾部文本里出现多个条件（如 `止损值30%，止盈值60%`）→ 逐条建成多条规则（止损、止盈各一条），这与回落链式不同；
   - 但**条件开仓（new 规则）一条只能承载一个条件**：尾部出现多个且无法判断主次时，向用户确认采用哪一个，不要自行合并或建多条 new 规则。
4. 边界消歧：条件里出现的数字按句式自身解释（价格条件里的数字=价格阈值，`%`=比率）；若一个数字既可读成下单数量又可读成条件阈值，按 2.0 严格规则追问。

**条件中的标的 → `condition_instrument`（解析时必须由 agent 归一）**

> 后端规则写入时对 `condition_instrument` **原样存储、不做大写/符号归一**（仅 new 规则的下单标的会按所归一）。因此下列转换必须在解析阶段由 agent 完成：

| 条件里写的标的 | condition_instrument |
|----------------|----------------------|
| 裸币种 `btc` / `eth` / `sol`（价格涨跌、ROI 类） | 一律转大写币安永续符号：`BTCUSDT` / `ETHUSDT` / `SOLUSDT`（即便指令是 deribit，也按跨所引用 `BTCUSDT` 处理） |
| 完整合约名 `ETH-18SEP26-2550-P` 价格突破/跌破 | 原样用 `ETH-18SEP26-2550-P`（deribit 适配器原样透传） |

**条件句式 → 字段词典**

| 口语 | condition_kind | operator | value | condition_instrument |
|------|----------------|----------|-------|----------------------|
| X 价格涨过/超过 N | `price` | `>=` | N（绝对价格） | 按上表归一 X；**new 规则必须显式填，勿留空** |
| X 价格跌破 N | `price` | `<=` | N | 同上 |
| X 仓位大于 N | `position` | `>` | N | 按上表归一 X |
| X 仓位盈利/ROI 大于 N% | `roi` | `>=` | `n/100` | 按上表归一 X |
| X 仓位亏损 N% | `roi` | `<=` | `-n/100` | 按上表归一 X |
| 关联仓位 X（被平掉） | `position` | `==` | `0` | X 原样（合约名或 `BTCUSDT`） |
| 盈利回落 N% | `profit_drawdown` | `>=` | `n/100` | 留空（链式后继规则用） |
| 止损值 N% / 止盈值 N% | `roi` | `<=`/`>=` | `-n/100` / `n/100` | 留空（本仓位标的） |

> - **new 规则开仓前无持仓**：即使条件标的与下单标的相同，`condition_instrument` 也要显式填写（留空会被当作"本仓位标的"，空上下文下永不触发）。
> - agent 只负责按词典如实解析发送；条件能否被判定、跨标的口径是否支持由后端负责，后端拒绝时原样展示 `message`，不自行删改条件。

### 2.5 风控平仓量写法

风控指令在标的后可带一个**可选的平仓量**（百分比或绝对数量）。文档中的 `[平仓量]` 表示"此处可写可不写"——方括号只是可选标记，**实际指令中不要带方括号**，直接写 `50%` 或 `5`：

| 实际写法 | 字段 |
|------|------|
| `n%`（如 `风控 D BTCUSDT.P 20% 止损…`） | `quantity_pct: n/100`（按比例平仓，`20%`→`0.2`） |
| `n`（如 `风控 D ETH-… 5 止损…`） | `quantity: n`（按绝对数量平仓，`5`→`quantity:5`） |
| 不写平仓量 | **默认全平**：`quantity_pct: 1` |

> 该平仓量对**本次指令创建的每一条 risk 规则统一生效**——包括一条指令里的止损、止盈以及 3.6.4 回落批量中的**每一条**：带 `5` 则批量里 arm / trail 两条都带 `quantity:5`，带 `20%` 则都带 `quantity_pct:0.2`；**不要照抄写死全平的模板**。

### 2.6 触发词与位置约定

| 意图 | 触发词 / 位置 |
|------|---------------|
| 即时开仓（市价） | 前缀 `市价开仓` |
| 即时开仓（限价） | 前缀 `限价开仓`；裸 `开仓` 默认限价（带价格位） |
| 条件开仓（市价 new 规则） | 前缀 `市价条件开仓`；尾部整段文字即条件，`order_type:"market"` |
| 条件开仓（限价 new 规则） | 前缀 `限价条件开仓`；尾部整段文字即条件，`order_type:"limit"` |
| 创建风控 | 前缀 `风控` / `risk` / `止盈止损`，或后缀 `{交易所} {账户} {标的} 止盈止损，…`；条件在最后部分 |
| 查询云盯盘规则 | `/watch-list [交易所] [用户] [开仓\|风控\|全部]`；`盯盘规则` / `仓位规则` 同此（**含「规则/watch」字样走此意图**） |
| 查询仓位 | `{账户} 仓位列表` / `仓位查询` / 裸 `仓位`（不带「规则」） |
| 查询风控 | `{账户} 止盈止损配置` / `风控查询` / `风控列表`；账户名后的 `risk` 也按查询处理 |
| 查询订单 | `{账户} 订单列表` / `订单查询` / `订单` |
| 取消挂单 | `{交易所} {账户} {标的} 取消挂单` / `取消订单` |
| 停用风控 | `停用止盈止损` / `取消止盈止损`（两者等价，注意与「取消挂单」区分） |
| 未设置风控仓位筛查 | `{交易所} {账户} 未设置风控仓位` / `无风控仓位`（可加前缀 `查看`，如 `查看 d test_deribit 无风控仓位`）；详见 §3.10 |
| 命令重放 | `/x [symbol] 开仓\|risk`（**类型必带**；详见 §3.8）；换标的重放上次开仓/风控 |

> 消歧：句首的 `风控|risk|止盈止损` = 创建风控；账户名之后的 `risk` = 查询风控。
> 「仓位规则 / 盯盘规则」（含「规则」）= 云盯盘规则查询（§3.5.1）；裸 `仓位`（无「规则」）= 查询持仓。
> 「取消挂单/取消订单」针对未成交订单（走撤单）；「取消止盈止损/停用止盈止损」针对 risk 规则（置 retired）。

### 2.7 写操作两条铁律（最高优先级，凌驾于"尽快完成"之上）

1. **发送前必须显式确认**：所有**查询以外**的功能——下单（市价/限价/条件开仓）、平仓、撤单（取消挂单）、创建/停用 risk 规则——在**真正向后端发出请求之前**，必须先把将要执行的内容（要素清单/订单或规则列表）以表格显式展示给用户，**只有用户明确确认（`y`）后才允许调用接口**；用户未确认或否认（`n`）时不得发送。批量（多笔撤单、批量规则）需整体回显、整体确认，不得拆成小步绕过确认。
2. **出错原样返回，禁止自行改写重发**：请求一旦失败（`code != 0` 或网络/交易所错误），必须把后端返回的 `message`（及错误码）**原样展示给用户**，由用户决定下一步；**严禁 agent 自行修改参数、替换字段、换符号/数量后自动重发同一请求**。即使用户原指令看似有明显笔误，也应先原样返回错误，再向用户说明并请其确认是否调整。

> 这两条适用于本 skill 全部写操作；各功能详情中的"回显确认表、等 y"与"原样展示 message"均是其具体化，不另行豁免。

### 3.1 账户查询

- **GET** `/api/v1/accounts`（可选 query：`exchange`/`name`/`is_testnet`/`position_mode`）；只返回非敏感字段，绝不会有 api_key/secret。
- 账户不确定时先用本接口校验/让用户选；下单查仓建规则前 account 必须确定。字段与展示见 `reference/api-orders.md` §3.1。

### 3.2 开仓（即时）

- **POST** `/api/v1/orders`；异步：立即返回内存 `PLACING`，终态用 GET /orders 轮询（`PLACING→NEW→PARTIAL→FILLED`，失败 `REJECTED`/`UNKNOWN`）。
- `quantity` 与 `order_cash` **二选一**；`{n}x`→leverage、`{n}u`→order_cash（名义金额、非保证金，服务端换算数量，agent 不换算）；`reduce_only` 仅平仓为 true；不接受客户端传 `client_order_id`。
- **三所形态差异**（指令模板、参数全表、curl 示例见 `reference/api-orders.md` §3.2）：
  - **binance**（现货/U 本位永续）：有「现货/合约」词位、有杠杆、金额或数量二选一；
  - **deribit 期权**：`instrument_type:"option"`，无杠杆/金额，只认张数（裸数字→`quantity`）；
  - **CTP**：只认**正整数手数**，禁止 `{n}u`/`{n}x`，合约号原样透传；上期所/能源中心品种不支持市价 → 引导改限价，拒单按 §2.7 原样返回。
- **account 词位必填**：缺失先追问、禁止不带 account 发请求（全交易所生效；hyperliquid 未接通时如实告知、不发请求）。
- 写操作：回显确认表、用户 `y` 后才 POST。

### 3.2.1 条件开仓（单条 new 规则）

- **POST** `/api/v1/rules`，**单对象** `rule_type:"new"`、`action:"self"`；触发动词定 `order_type`（`市价条件开仓`→market / `限价条件开仓`→limit）。
- 条件取指令尾部文字（§2.4）；**一条 new 规则只承载一个条件**，多条件且无主次时追问。
- **`condition_instrument` 必须显式填**（即使与下单标的相同，裸币种 agent 转大写）；下单要素各所形态同 §3.2。
- curl 模板与各所示例见 `reference/api-orders.md` §3.2.1；创建前回显确认。

### 3.3 平仓（全部/部分，即时）

- 无独立平仓接口：**先 GET /positions 取 side/quantity/instrument → 反向 + `reduce_only:true` 下市价单**（POST /orders）；全平=仓位量，部分=仓位量×比例。
- **CTP**：数量必须正整数手数；「持仓手数×比例」非整数时先与用户确认，不自行取整。
- 「到价/到比例自动平仓」不走这里，走 risk（§3.6）。步骤与 curl 见 `reference/api-positions.md` §3.3。

### 3.4 仓位查询

- **GET** `/api/v1/positions`（可只传 account 不传 exchange）；单条 **GET** `/api/v1/positions/{id}`；交易所快照 **POST** `/api/v1/exchange/positions`（默认不写内存）。
- 返回字段 **`id` 即创建 risk 用的 `position_id`**；`roi` 为保证金收益率（口径 §2.3）。
- **hedge 双向持仓多/空各一行、不做净仓合并**；行情来自对账流水线，刚下单立即查可能未反映。
- query/PositionDTO 字段/展示样例见 `reference/api-positions.md` §3.4。

### 3.5 止盈止损查询

- **GET** `/api/v1/rules` 固定加 `rule_type=risk`，默认仅未终止；可只传 account。
- **规则行不带标的/方向**：展示前批量查一次 GET /positions，用 `position_id == 仓位.id` 关联。
- 字段、条件格式化（roi 保证金收益率口径）、展示见 `reference/risk-rules.md` §3.5。

### 3.5.1 云盯盘规则查询（/watch-list）

- 语法 `/watch-list [交易所] [用户] [开仓|风控|全部]`，**纯查询、只读**；交易所与用户必传，缺则追问；类型缺省=不传 `rule_type`。
- **status 多值参数当前不可用**：不传 `status`，取默认未终止全集后客户端只留 `active/pending`（剔除 in_use/retired）；new 行直读字段，risk 行关联仓位。
- curl/过滤/输出表见 `reference/risk-rules.md` §3.5.1。

### 3.6 创建止盈止损（watch_rule · risk）

- **POST** `/api/v1/rules`；公共必填：`account`、`rule_type:"risk"`、`position_id`、`condition_kind`、`operator`、`value`；**不传 side/instrument**。
- 前置：先查仓位拿 `position_id`（多空多行让用户选，无仓提示先开仓）；`exchange` 币安可省，**deribit/ctp 必传**（否则报 40002）。
- 五类条件见 §2.3 条件表；ROI 按保证金收益率（§2.3）；平仓量写法与「对本次每条规则统一生效」见 §2.5。
- **回落止盈**：必须 **POST `/api/v1/rules/batch`** 一次发 `{rules:[arm, trail]}`（arm `action:"rule:trail"`、trail `pending:true` + `profit_drawdown`），服务端回填真实 rule id；同指令还含独立止损时再 POST 一条单规则。禁止拆多次手动调用再猜 id。
- 指令形态、各所注意（含 CTP 整数手数）、curl 模板、确认与展示见 `reference/risk-rules.md` §3.6。

### 3.7 取消（停用）止盈止损

- **POST** `/api/v1/rules/status` 置 `retired`（等价 deleted=true），**本功能只停用**。
- `ids` **必须取自本次命令刚查询的 GET /rules 新鲜结果**，禁止用旧列表；支持 `{ids:[...]}` 或 `{items:[{id,status}]}`。
- symbol 路径停用该标的全部生效规则；交互路径列序号让用户选。流程与回显见 `reference/risk-rules.md` §3.7。

### 3.8 命令重放（/x）

- 语法 `/x [symbol] 开仓|risk`：**类型必带**（缺/错词→追问，禁止猜）；交易所由 symbol 形态判定（USDT→binance、期权名→deribit、`rb2510` 类→ctp），不能唯一归属则追问。
- payload 复用记忆 `reference/last_commands.json`（按所分组、含 endpoint/method/body），**不再重新解析自然语言**；只在确认并发送成功后记 open/risk，查询/撤单/平仓/停用//x 本身不记。
- **risk 重放必须按新 symbol 重查 position_id**（不沿用旧值，无仓终止）；new 自引用条件标的同步替换，跨标的条件不变。
- 先回显**替换后**完整要素（不做新旧对比）、用户 `y` 后才执行；无对应槽位告知后结束。完整规则与记忆 JSON 见 `reference/workflows.md` §3.8。

### 3.9 订单查询与撤单

- **GET** `/api/v1/orders`：默认只看活跃挂单，**必须带** `status[]=NEW` & `status[]=PARTIAL`（方括号写法，裸 `status=` 后端不认）；用户明确要全部/历史才放开。
- **DELETE** `/api/v1/orders`：`client_order_id`/account/exchange 走 **query**，不读 JSON body；**只能逐笔撤，不支持按标的一键批量撤**。
- 「{所}{户}{标的} 取消挂单」：先查该标的 NEW/PARTIAL → 回显等 `y` → 逐笔 DELETE 汇总；无挂单直接告知。query/展示见 `reference/api-orders.md` §3.9。

### 3.10 未设置风控仓位筛查与批量设置

- 触发：`{交易所} {账户} 未设置风控仓位` / `无风控仓位`。
- **筛查（纯查询直接执行）**：GET /positions 活跃仓位 与 GET /rules（risk）按 position_id 求差集，逐仓位行判定（不按 instrument 合并），带序号表格展示；全部有风控则告知并结束。
- **批量设置（写操作，必须回显确认）**：默认规则 = 回落止盈「盈利55%回落5%触发」+ 独立止损「亏损30%」、全平；用户可自带规则与平仓量（解析表见 `reference/risk-rules.md` §3.10），未带平仓量时确认表必须写明「默认全部数量平仓」。
- 每仓位回落走 `/rules/batch`、止损走 `/rules`；**单仓失败直接跳过不重试**（§2.7），结束统一汇总。

## 5. 错误处理

统一信封 `{ code, message, data }`：成功 `code=0`；非 0 时 `data=null`，把 `message` **原样**展示给用户并给建议，不臆测原因、**不自行改参数自动重发**（铁律 §2.7）。

常见 code：`40001` 参数缺失/非法、`40002` 账户/交易所未配置、`40004` 资源不存在、`40901` 状态冲突（重复 client_order_id、规则状态非法迁移）、`50001` 交易所调用失败、`50002/50000` 内部错误。

信封示例与展示形态见 [`reference/workflows.md`](reference/workflows.md) §5。

## 6. 限制说明

1. 主机地址从 config 的 `api.base` 读，禁止硬编码；接口路径以本文件为准（仓位 `/api/v1/positions`、账户 `/api/v1/accounts`）。
2. 所有调用用 curl；响应用表格展示；规则 id / 仓位 id 在需要让用户选仓位或停用时内部使用，常规结果表不向用户展示内部大 id（用序号呈现）。
3. 百分比必须由用户以 `n%` 输入，agent 换算为比率；**ROI 条件按保证金收益率表示**（止损 30%→`-0.3`、止盈 60%→`0.6`），具体换算由后端完成（见 §2.3）。
4. risk 规则必须先查仓位拿到 `position_id`，不允许让用户手填数字 id；risk 不传 side/instrument；`exchange` 币安可省、deribit / ctp 等非默认所必传。
5. 条件开仓为**单条** new 规则（`action:"self"`，条件与下单要素同规则、命中当轮下单），触发条件从指令**尾部整段文字**提取（不强制 `==…==`，详见 2.4）；`condition_instrument` 仅 new 规则须显式填；binance 可用数量/金额（order_cash）+杠杆，deribit 只要张数，**ctp 只要正整数手数（quantity）、无金额/杠杆**。平仓量方括号 `n%`/`n`/缺省（全平；方括号仅为可选标记，实际指令直接写 `20%` 或 `5`）。
5b. **CTP 专项口径**：交易所仅识别 `C`/`ctp`/`CTP`→`ctp`，`instrument_type:"futures"`；合约号原样透传、大小写敏感（`rb2510` 等，不补 USDT/不大写）；开仓/平仓只接受正整数手数，小数手数拒单；不解析、不下发 `{n}u`（order_cash）与 `{n}x`（leverage），用户给了金额/杠杆先追问改报手数；上期所/能源中心品种不支持市价单（柜台拒），用限价。
6. 写操作（下单、建规则、停用、平仓、撤单）**除查询外**：①发送前必须表格回显、用户 `y` 后才发请求；②失败原样返回 message，**不得自行改参数重发**（铁律见 2.7）。
7. 停用规则的 ids 必须取自本次刚查询的 GET /rules；停用状态用 `retired`，且只做停用。
8. 回落止盈必须向 **`POST /api/v1/rules/batch`** 发 `{rules:[...]}` 批量 + `action:"rule:<ref>"` + 后继 `pending:true`，不要拆成多次手动调用再猜 id，也不要发到 `/rules`（该端点不认 `rules` 数组）。
9. 双向持仓（hedge）多空是两行独立仓位，分别查、分别设规则，不做净仓合并。
10. 未设置风控仓位筛查（§3.10）：筛查为纯查询可直接执行；后续批量设置属写操作，必须回显确认后才发请求；单个仓位失败直接跳过不重试，结束后统一汇总结果。
10. 账户由服务端 account.csv 配置，本 skill 不含创建用户。
11. `/watch-list`（§3.5.1）：规则接口的 `status` 多值参数当前不可用——裸 `status=` 报 400、`status[]=` 被静默忽略；故查询不传 status、取默认未终止全集后客户端只留 active/pending。类型用单值 `rule_type=new/risk`（该参数正常）。
12. `/x`（§3.8）：`开仓|risk` 类型必带、缺一追问；交易所由 symbol 判定，只重放该交易所下确认后成功执行过的命令（记忆按交易所分组在 `reference/last_commands.json`），账户沿用记录。risk 重放必须按新 symbol 重查 position_id，不沿用旧值。任何情况下先回显、用户 `y` 后才实际操作，无确认绝不执行。
