# 执行规则

本文件定义验收测试的执行约束：账号白名单、自动确认、标的与价格适配、触发观察、状态清理、证据格式。

---

## §1 账号白名单

### 1.1 白名单

| 账号 | 交易所 | 说明 |
|------|--------|------|
| `test_binance` | binance | 币安测试账户 |
| `test_deribit` | deribit | Deribit 测试账户 |
| `ctp-simnow` | ctp | SimNow 仿真账户 |

匹配规则：去掉首尾空白后**精确匹配**（大小写敏感）。`ctp_simnow`、`ctp-sim`、`simnow` 等变体均**不**自动视为白名单。

### 1.2 识别账号

- 从测试项原文提取账户词位。常见形态：`风控 B test_binance BTCUSDT …`、`市价开仓 C ctp-simnow rb2701 long 1`。
- 一个测试项出现多个不同账号 → 视为歧义，按 §1.4 让用户确认。
- 文档未写账号 → 按交易所映射（见下表），并写入报告「前置调整表」。

| 交易所 | 未指定时的默认账号 |
|--------|-------------------|
| binance（B / 币安） | `test_binance` |
| deribit（D） | `test_deribit` |
| ctp（C / ctp / CTP） | `ctp-simnow` |

### 1.3 非白名单处理（强制停止）

识别到非白名单账号时，**先停止执行**，输出以下信息：

```
⚠️ 检测到非白名单测试账号，已暂停验收执行。
- 测试项：<编号与原文>
- 识别到的账号：<账号名>
- 允许的账号：test_binance / test_deribit / ctp-simnow
请确认是否允许使用该账号执行测试（回复"确认使用 <账号名>"）；未确认前不会发送任何写操作。
```

用户明确确认后：
- 在报告该项「前置调整表」记录「用户授权使用非白名单账号 <账号名>（时间）」；
- 仅该项授权，不扩散到其他测试项；
- 若用户拒绝 → 该项记 BLOCKED，原因「非白名单账号未获授权」。

### 1.4 账号歧义

同一测试项出现多个账号（如先写 `test_binance` 后写 `test_deribit`）且无明确归属 → 暂停并询问用户该测试项使用哪个账号；未得到答复前记 BLOCKED。

## §2 自动确认协议

用户调用本 skill 即视为**授权本次验收测试中的写操作**，包括：市价/限价/条件开仓、平仓、撤单、创建/停用 risk 规则。

### 2.1 执行方式

1. 通过 `Skill` 调用 `trade-ops`，传入完整自然语言指令。
2. trade-ops 按自身流程回显确认表并要求 `y` 时，**直接回复 `y`**。
3. 把回显表内容（要素、规则列表、订单列表）快照到报告的「执行回显」字段。

### 2.2 自动确认的边界

- **仅覆盖「确认执行」**：确认表内容与本测试项一致时回复 `y`。
- **不覆盖歧义追问**：trade-ops 追问方向、价格、数量、账号、仓位选择时，不得猜：
  - 文档能明确消歧 → 用文档要素回答；
  - 文档无法消歧 → 该项记 BLOCKED，原因写清缺什么。
- **不覆盖跨项批量**：不得为了让 trade-ops 少问几次而把多个测试项合并成一次批量写操作。
- 若确认表与测试项预期不符（例如价格被解析成了数量）→ **不回复 `y`**，先修正指令重新调用；修正属于前置调整，记入报告。

### 2.3 失败处理

- trade-ops 返回非 0 `code` 或交易所错误 → 原样记录 `message` 与错误码，该项判 FAIL（环境不可用则 BLOCKED）。
- **禁止**自行改参数后重发同一请求；确需调整时，作为一次新的「前置调整后的执行」记录，且说明调整理由。

## §3 标的适配

### 3.1 流动性标的基线

优先使用下列标的；文档指定标的可操作且流动性足够时，保留原标的。

| 交易所 | 推荐标的 | 备注 |
|--------|----------|------|
| binance | `BTCUSDT`、`ETHUSDT`、`SOLUSDT` | U 本位永续，`instrument_type=futures` |
| deribit | 近月平值期权（如 `BTC-<最近到期>-<现价附近行权价>-C/P`） | 以当前实际可交易合约为准；无报价则换下一档行权价 |
| ctp | 主力合约：`rb2701`、`cu2612`、`au2612`、`i2701`、`m2701`、`TA701`、`MA701`、`IF2612` | 以 `config/venue.toml` 的 `preset_dominants` 或当日行情主力为准 |

> CTP 合约月份会轮换；表中为 2026-11-05 配置基线。执行前用现价脚本确认该合约有行情（无行情 ≠ 一定无效，可能休市，需结合交易时段判断）。

### 3.2 不可操作标的的替换

满足任一条件即替换：
- 文档标的已到期、非当前主力或不存在；
- 期权无买卖报价、点差过大；
- 品种不支持该测试项的操作（如某些品种有最小手数/保证金限制导致无法开 1 手）；
- 下单被柜台以「合约不可交易」拒绝。

替换规则：
1. 一次只替换一个测试项的标的，不影响其他项；
2. 映射到同交易所、同 `instrument_type` 的流动性标的；
3. 报告「前置调整表」记录：`原标的 → 新标的 | 原因 | 现价`；
4. 替换后重新推导价格与触发阈值（§4）。

### 3.3 各所形态注意

- **binance**：数量与金额二选一（`{n}u` 为名义金额），杠杆 `{n}x`。
- **deribit**：只认张数；指令不要出现杠杆/金额；风控请求必须带 `exchange:"deribit"`。
- **ctp**：只认正整数手数；禁止 `{n}u` / `{n}x`；合约号大小写敏感、原样透传；风控请求必须带 `exchange:"ctp"`。SHFE/CFFEX/CZCE 的市价单由适配器转对手价限价，正常可测。

## §4 价格与触发条件适配

### 4.1 获取现价（只读）

```bash
# 服务地址与密钥按下方优先级合并，缺省读 trade-ops config.yaml
python3 {trade-acceptance 技能目录}/reference/scripts/last_price.py \
  --exchange binance --symbol BTCUSDT
# 远程示例：
# python3 .../last_price.py --exchange ctp --symbol rb2701 \
#   --base ws://127.0.0.1:9100 --key-file /secure/south.key
```

**配置优先级（仓库外用户配置，git pull 不冲突）**

| 项 | 优先级（高 → 低） |
|----|------------------|
| 服务地址 | `--base` > `TRADE_API_BASE` > `~/.config/trade-acceptance/config.yaml` 的 `api.base` > trade-ops `reference/config.yaml` 的 `api.base` > 本机默认 |
| 密钥路径 | `--key-file` > `SOUTH_KEY_FILE` > `TRADE_SERVICE_DATA_DIR/south.key` > 用户配置 `south.key_file` > `./data/south.key` |

用户级配置示例（`~/.config/trade-acceptance/config.yaml`，自行创建，**不要放进任何仓库**）：

```yaml
api:
  base: "http://127.0.0.1:9100"
south:
  key_file: "/secure/south.key"
```

输出示例（合成值）：

```json
{"exchange":"binance","symbol":"BTCUSDT","close":85000.0,"end_time":1763424000000,"source":"get_klines"}
```

回退顺序：
1. 现价脚本（连接交易服务的南向 WS `get_klines`，取该服务本地留存的最新 1m 收盘价；**不直连交易所**）；
2. 同标的仓位的 `current_price`（通过 trade-ops 仓位查询/交易所实时仓位）；
3. 以上都不可用 → 该项 BLOCKED，原因「无法获取现价」。

### 4.2 限价单价格

| 测试意图 | 买单价 | 卖单价 |
|----------|--------|--------|
| 只验证挂单（不要求成交） | 现价 × 0.990 | 现价 × 1.010 |
| 要求尽快成交 | 现价 × 1.001（穿价） | 现价 × 0.999（穿价） |

- CTP 按最小变动价位取整（价格精度以合约 tick 为准，避免非法价格被拒）。
- 报告记录实际提交价与现价。

### 4.3 价格条件开仓阈值

- 市价条件开仓：阈值设在现价附近以**尽快触发**——「涨过」用 `现价 × 0.999`，「跌破」用 `现价 × 1.001`。
- 限价条件开仓：同样把触发阈值贴近现价；命中后的限价单价格按 §4.2 的「要求尽快成交」设置，确保能观察到订单。
- 若测试文档明确要求验证「不触发」行为，则阈值远离现价，并等待固定观察窗（如 3 分钟）后确认未触发。

### 4.4 价格类风控阈值

| 规则 | 阈值设置（尽快触发） |
|------|---------------------|
| 价格涨过止盈 | 现价 × 0.998（略低于现价，创建后很快满足） |
| 价格跌破止损 | 现价 × 1.002（略高于现价） |

- 需要验证规则长期生效而不触发时，阈值取现价 ±2%~5%，观察窗口内不应触发。

### 4.5 ROI / 回落条件收紧

文档常见苛刻值（盈利 20% 回落 5%、止损 30%）在验收时段内难以触发，默认收紧：

| 条件 | 文档值 | 验收用值 |
|------|--------|----------|
| 止盈 ROI | ≥ 20% | ≥ 0.5% |
| 回落止盈 | 盈利 20% 回落 5% | 盈利 0.5% 回落 1% |
| 止损 ROI | ≤ -30% | ≤ -1% |
| 价格风控 | 现价 ±5% | 现价 ±0.2%（见 §4.4） |

配套手段：
- 验收默认 **3x 杠杆**（风控规则按 ROI 口径，3x 下 ROI 0.5% ≈ 价格波动 0.167%，更易触发）；标的选波动与流动性适中的（如 SOLUSDT）。文档另有指定时以文档为准；
- 若 2 分钟内未触发，可继续等待至超时，不做「人为砸盘/拉盘」。

所有收紧写进「前置调整表」，不要改原文档。

### 4.6 触发超时

| 类型 | 默认最长等待 | 轮询间隔 |
|------|--------------|----------|
| 价格条件开仓 | 10 分钟 | 5 秒 |
| 价格类风控 | 10 分钟 | 5 秒 |
| ROI / 回落止盈 / 关联仓位 | 15 分钟 | 5 秒 |

超时 → 该项 BLOCKED，附最后观测值（现价、roi、max_roi、profit_drawdown、规则状态）。

## §5 触发观察

### 5.1 通用观察链

1. **规则存在**：通过 `trade-ops` 查询盯盘规则（`/watch-list {ex} {account} 全部`）或风控查询，确认规则已创建、状态与参数正确、`position_id` 绑定正确。
2. **条件命中**：轮询仓位/规则，观察 `roi`、`max_roi`、`profit_drawdown`、规则状态变化（`active → in_use/retired`）与仓位 `rule_id`。
3. **动作结果**：查询仓位与订单，确认平仓/开仓动作真实发生，数量、方向、价格符合规则。
4. **收尾状态**：规则终止状态、仓位剩余数量、订单终态。

### 5.2 各测试项观察重点

| 测试项 | 观察重点 |
|--------|----------|
| 市价下单 | 订单 `PLACING→NEW→FILLED`；仓位数量 = 订单成交量；方向正确 |
| 限价下单 | 订单 `NEW`；`order_price` = 提交价；未成交形态下 `filled_quantity=0`；如要求成交则轮询 FILLED |
| 查找仓位 | 列表包含该账户全部活跃仓位；`quantity/pos_price/current_price/roi` 字段完整；与交易所实时仓位一致 |
| 止盈配置 | 规则 active；`condition_kind=roi/price`；`operator/value` 与指令一致；绑定仓位正确 |
| 回落止盈 | 批量返回两条：arm `active`（`action=rule:trail`）、trail `pending`（`profit_drawdown`）；触发后 arm→retired、trail→active；trail 命中后仓位平仓数量正确 |
| 止损配置 | 规则 active；`roi <= -n%`；触发后仓位平仓 |
| 幂等 | 第二次相同指令后，有效规则数量是否仍为 2（不含重复）；重复规则是否同参、同仓位、同状态 |
| 价格风控 | `condition_kind=price`；`operator/value` 正确；触发后仓位平仓 |
| 关联仓位风控 | `condition_kind=position`、`operator==`、`value=0`、`condition_instrument=关联标的`；主动平掉关联仓位后本仓位被平掉 |
| 市价条件开仓 | new 规则 active；触发后生成市价订单、建仓成功、规则转 in_use/retired |
| 限价条件开仓 | new 规则 active；触发后生成指定价限价订单（NEW 或 FILLED） |
| 查找盯盘规则 | 仅返回 `active/pending`；开仓/风控分类正确；与 `GET /rules` 交叉核对一致 |

### 5.3 回落止盈专项

回落止盈是链式规则，必须分阶段观察：
1. 创建后：arm 规则 active、trail 规则 pending，两条均绑定同一 `position_id`；
2. 盈利达到 arm 阈值后：arm 变 retired，trail 变 active；
3. 盈利自峰值回落达到阈值后：trail 触发平仓；
4. 平仓后：仓位数量减少（按 `quantity`）或归零（按 `quantity_pct`），方向正确，订单终态 FILLED。

任何一阶段未按预期推进 → FAIL（若因行情未达到阈值 → BLOCKED，并记录 max_roi / profit_drawdown）。

### 5.4 关联仓位专项

1. 创建关联规则后，确认 `condition_instrument` 为关联标的；
2. 用 trade-ops 平掉关联标的仓位（这一步是测试步骤，须记录指令与结果）；
3. 轮询本仓位，确认在关联仓位数量归零后被平掉；
4. 记录两个仓位平仓的时间顺序与数量。

## §6 状态清理

每个测试项结束后执行，顺序固定：

1. **停用规则**：`trade-ops` 停用本项创建的 risk / new 规则（按本次记录 id；仅停用本项，不动其他规则）。
2. **撤销挂单**：查询该账户 NEW/PARTIAL 订单，逐笔撤单（只撤本项产生的订单）。
3. **平掉仓位**：查询本项开出的仓位，反向 `reduce_only` 平仓；CTP 按整数手数。
4. **复核**：确认规则 retired、订单 CANCELED、仓位已平。

记录到报告「清理记录表」：时间、动作、对象、结果。清理失败不改变测试项结论，但必须在「遗留问题」中列出。

例外：文档明确要求「保留现场观察」时，不清理，在报告中注明残留状态。

---

## §7 证据格式

每个测试项至少记录：

1. **执行指令**：传给 trade-ops 的完整自然语言指令原文；
2. **执行回显**：trade-ops 的确认表快照（要素/规则/订单）；
3. **接口证据**：关键接口返回摘要——`code`、订单状态、仓位数量/ROI、规则 id/状态/条件；
4. **时间线**：执行时间、触发时间、清理时间（`YYYY-MM-DD HH:MM:SS`）；
5. **清理结果**。

> 证据中不记录 API Key、Secret、Passphrase 等敏感字段；账户仅记账号名。

## §8 文档适配

- 文档缺「预期结果」→ 使用 `test-items.md` 基准期望补全，并在报告中标注「期望来源：基准」。
- 文档缺「实际结果/测试结论」→ 测试后填充。
- 文档给的是自然语言测试项（非表格）→ 逐条拆分为独立测试项，编号保持文档顺序。
- 文档包含 12 项之外的额外测试项 → 按同一流程执行；无法映射到 12 项时，按原文语义选择最接近的 trade-ops 指令，并在报告中说明映射依据。
