## 连接设计

1. **服务端配置 `SECRET_KEY`**

   服务端为每个策略客户端配置一个共享密钥 `SECRET_KEY`。

2. **客户端生成一次性 `nonce`**

   每次建立 WebSocket 连接时，客户端随机生成一个足够长且不可预测的 `nonce`。

3. **客户端生成 HMAC 签名**

   客户端使用：

   ```text
   signature = HMAC-SHA256(
       strategy_name + nonce,
       SECRET_KEY
   )
   ```

   生成签名。

4. **连接时携带认证信息**

   客户端在 WebSocket Upgrade 请求中携带：
   
   ```text
   strategy_name
   nonce
   signature
   ```

   例如：
   ```text
   strategy_name = btc_strategy
   nonce         = 8f31c2...
   signature     = a91e7d...
   ```

5. **服务端验证**

   服务端收到连接请求后：
   ```text
   strategy_name + nonce + signature
             ↓
      检查 nonce 是否已使用
             ↓
      重新计算 HMAC-SHA256
             ↓
      使用恒定时间比较校验 signature
             ↓
          验证成功？
          ↙        ↘
        是          否
        ↓            ↓
   升级 WebSocket    拒绝连接
        ↓
    注册策略连接
   ```

6. **Nonce 生命周期**

   验证成功后，服务端将 `nonce` 标记为已使用，并设置合理的 TTL。

   例如：

   ```text
   nonce: 8f31c2... → used → TTL 5min
   ```

   同一个 `nonce` 再次出现时直接拒绝，从而防止重放攻击。

7. **签名比较**

   服务端必须使用恒定时间比较，例如 Go：

   ```go
   hmac.Equal(expectedMAC, receivedMAC)
   ```

   避免普通字符串比较产生时序侧信道。

### 认证信息

```text
strategy_name
nonce
signature
```

其中：

```text
signature =
    HMAC-SHA256(
        strategy_name + nonce,
        SECRET_KEY
    )
```

### 安全性

* `SECRET_KEY` 永远不会通过网络传输。
* HMAC 用于证明客户端持有正确的 `SECRET_KEY`。
* `nonce` 用于防止认证请求被重复使用。
* `hmac.Equal` 用于降低签名比较产生的时序攻击风险。
* WebSocket 连接本身应使用 TLS，即 `wss://`，防止认证信息在传输过程中被窃听或篡改。

## 核心设计原则
1.验证前置​ — 在 WebSocket 升级完成之前完成所有验证，非法连接连握手都走不完。
2.验证通过才分配资源​ — 不信任的连接不创建 channel、不插入 registry、不 spawn 任务。
3.签名即意图​ — HMAC 的输入包含策略名，签名与具体操作绑定，改策略名即失效。
4.恒定时间比较​ — 签名校验使用恒定时间算法，防时序攻击逐字节爆破。
5.连接时绑定，非每消息验证​ — 握手阶段确定策略身份，后续消息直接路由，不再重复验签。
6.无状态验证​ — 纯本地 HMAC 计算，不依赖数据库/Redis/外部存储，可水平扩展。
7.最小暴露面​ — 验证失败返回统一错误，不区分原因，不泄露策略名、签名格式等内部结构。
9.策略即插件​ — 策略处理逻辑与连接管理解耦，新增策略无需修改连接层代码。

## 设计约束
1. 不要使用channel来在任务传递数据
2. 支持多 strategy / 多交易所实例高并发接入
