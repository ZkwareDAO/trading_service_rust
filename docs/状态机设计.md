# 状态机设计（订单 / 仓位 / 规则）

> 本文档汇总三个核心实体的状态机与状态流转，基于代码同步：
> - 订单：`crates/trading-models/src/order.rs`（`OrderStatus`）、`crates/trading-store/src/orders.rs`（`OrderRepo` 状态推进）、`crates/trading-service/src/event.rs`（用户流回报入口）与 `crates/trading-service/src/rules/engine.rs`（REST 终态兜底）。
> - 仓位：`crates/trading-models/src/position_sync.rs`（`PositionDiff` 裁决）、`crates/trading-store/src/positions.rs`（`PositionRepo` 对账落库）。
> - 规则：`crates/trading-models/src/watch_rule.rs`（`WatchRuleStatus`）、`crates/trading-store/src/rules.rs`（`RuleRepo` 状态机）、`crates/trading-service/src/rules/engine.rs`（引擎扫描与链式激活）。
>
> 改动任一状态机时请一并更新本文。

## 1. 订单状态机

### 1.1 状态集合（`OrderStatus`）

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `PLACING`（默认） | 已写内存、尚未收到交易所应答 | 否 |
| `UNKNOWN` | REST 已发出但应答不确定（如下单超时），等待回报/兜底收敛 | 否 |
| `NEW` | 交易所已受理（挂单中） | 否 |
| `PARTIAL` | 部分成交 | 否 |
| `FILLED` | 全部成交 | **是** |
| `CANCELED` | 已撤销 | **是** |
| `REJECTED` | 交易所/前置拒绝，未受理 | **是** |
| `EXPIRED` | 订单过期（如止损单到期） | **是** |

终态判定 `OrderStatus::is_terminal`：`FILLED | CANCELED | REJECTED | EXPIRED`。
终态订单不再被任何回报推进。

### 1.2 触发订单状态变化的事件

| 触发源 | 说明 |
|---|---|
| 建单 `OrderRepo::insert` | 进入初始 `PLACING` |
| 用户流 WS `ORDER_TRADE_UPDATE`（币安） | 经 `event.rs` 按回报推进 NEW/PARTIAL/FILLED/CANCELED/EXPIRED |
| CTP 实时回报 / 插入错误帧 | 拒单收敛为 `REJECTED`（插入错误帧携带 `OrderRef`，或 `Cancelled`+拒单文案）；正常撤单仍 `CANCELED`；多腿单全部腿终态才收敛 |
| 下单 REST 失败、应答不确定 | `mark_unknown` 落 `UNKNOWN`（不臆造拒单） |
| REST 前置/连接失败 | `apply_rejection` → `REJECTED` |
| REST 终态兜底 `reconcile_terminal_orders` | 周期查单：查到明确终态即收敛；若 `apply_event` 因成交量差一个精度单位把 FILLED 降级为 PARTIAL，则 `force_terminal` 以交易所终态强制收敛并软删（成交量保持真实值） |

> 注意：Order 进入终态时**在同一次状态落库内自动 `deleted=1`**（`apply_terminal_lifecycle`，软删收口在 `apply_event` 的行锁闭包内，是唯一软删规则点）。终态行以 tombstone 保留当日，可用 `peek_by_cid`（含软删行）回查；跨日随内存 purge 进历史归档。同时终态释放 signal_id 在途占位，允许策略用同一 `signal_id` 修正重发。

### 1.3 UNKNOWN → REJECTED 的「查无」收敛（安全口径）

交易所查单明确应答 `-2013 Order does not exist` 时，**不立即**拒单；必须同时满足：

- 当前状态为 `UNKNOWN`；
- 订单年龄 `now - created_at ≥ 60s`（`NOT_EXISTS_GRACE_MS`，排除交易所主从延迟）。

满足后 `apply_rejection` → `REJECTED` 并 retire 关联规则。
纯决策：`should_reject_on_not_exists(status, age_ms)`。

### 1.4 成交量守卫与状态归一化

`apply_event` 行锁内（与状态变更同临界区）：

- 累计成交量**单调不减**、且**不超过委托量**（定点守卫）；
- 回报 `FILLED` 但累计成交量未达委托量（如 reduce_only 超仓时交易所只成交实际持仓）→ 如实标 `PARTIAL`，绝不把量补成委托量；
- 显式终态 `REJECTED/CANCELED/EXPIRED` 原样采用。
- **交易所明确终态但成交量差一个精度单位**（如 `order_quantity=0.002105`、
  `filled_quantity=0.0021`）会被上述规则降级为 `PARTIAL`，导致订单永远非终态、
  REST 对账每分钟重试。此时对账路径调用 `OrderRepo::force_terminal`：
  以**交易所返回的终态**覆盖状态并软删，`filled_quantity` 保持真实值，不补成
  委托量（2026-11-05 HL 订单 2096 事故）。

### 1.5 CTP 拒单与多腿终态收敛（2026-11-10）

- **插入错误帧**（如 `code=31 资金不足`）：柜台不再推 `OnRtnOrder`。网关用错误帧回显的 `OrderRef` 反查 cid，合成零成交终态快照后收敛为 `REJECTED`；无 `OrderRef` 的错误帧仍只记 `Error`，不臆测订单。撤单错误帧（24/25/26）不收敛订单。
- **受理后拒绝**（`OnRtnOrder(status=Cancelled)` 且 `StatusMsg` 命中「拒绝/废单/不足/涨跌停板…」）：由 `terminal_status_from` 改判 `REJECTED`；正常「已撤单」仍是 `CANCELED`。
- **多腿单**（SHFE 跨今昨，一单两腿）：`all_terminal && legs_complete` 才投影逻辑终态；一腿拒、一腿在挂时保持 `NEW`/`PARTIAL`，不误杀在途腿。零成交 + 拒单文案 → `REJECTED`；一腿成交 + 一腿撤/拒 → 终态 `CANCELED`（成交量/VWAP 保留），不再停留在非终态 `PARTIAL`。
- 物理腿通知（`ctp-leg`，多腿用户唯一可见播报）使用同一 `terminal_status_from` 口径。

实现：`crates/trading-exchange/src/ctp/venue.rs`、`crates/trading-exchange/src/ctp/gateway/spi.rs`。

### 1.6 简化流转

```
PLACING ──受理──> NEW ──全部成交──> FILLED
   │               ├──部分成交──> PARTIAL ──> FILLED
   │               ├──撤销──────> CANCELED
   │               └──过期──────> EXPIRED
   ├──前置/连接拒绝──────────────> REJECTED
   └──应答不确定──> UNKNOWN ──(查无 -2013 且≥60s)──> REJECTED
                     └──(回报/兜底明确终态)──> FILLED/CANCELED/EXPIRED
```

## 2. 仓位状态机

仓位**没有显式的 status 枚举**——生命周期由软删标记 `deleted` 与 `close_time` 表达：
`deleted=false` 为持仓中，`deleted=true` 且带 `close_time` 为已平仓 tombstone（当日保留、可回查）。

### 2.1 状态集合

| 状态 | 表达 | 含义 |
|---|---|---|
| 持仓中 | `deleted=false` | 活跃仓位，接受行情重估与规则绑定 |
| 已平仓（tombstone） | `deleted=true` + `close_time` | 对账软平仓保留行；当日可见（查询 `deleted=1` 可查），跨日 purge 归档 |

> 仓位主键即 `id`，是 risk 规则 `position_id` 绑定的对象；平仓后规则随仓位消失而 retired（见 §3）。

### 2.2 状态流转（对账裁决驱动）

仓位不由下单直接维护，而由**对账流水线**产生与推进（`PositionRepo::apply_diffs` / `upsert_matching`）：

| 触发源 | 说明 |
|---|---|
| ACCOUNT_UPDATE 脏信号去抖对账 | 去抖窗口（默认 500ms）合并后拉 `get_positions` REST 真值，diff 落库 |
| 定时全量对账 | 周期（默认 60s）全量兜底，无信号也强制执行 |
| （重）连补发 | 账户用户流重连后主动拉一次全量 |
| 行情重估 | 不改生命周期，仅刷新「同所+同类型+同标的」活跃仓位的估值衍生字段（current_price/notional/roi/max_roi/profit_drawdown） |

裁决结果为三种 `PositionDiff`（`position_sync.rs`）：

```
交易所快照 vs 本地内存
   ├── 交易所有、本地无 ──> Created（新建仓位，按快照当前价重估衍生字段）
   ├── 两边都有        ──> Updated（覆盖变动字段、保留本地账簿字段后重估）
   └── 本地有、交易所无 ──> Closed（软平仓：deleted=1 + close_time，tombstone 保留当日）
```

**同键重复行自愈**：对账 key 为 `(account, instrument, side, instrument_type)`。本地同一 key
若存在多条 `deleted=0` 行（历史脏数据/异常插入），`diff_positions` 不再用 HashMap 静默覆盖：

- 交易所仍返回该 key：保留 **keeper**（优先与远端 `quantity`/`pos_price` 一致的行；多条一致
  或无匹配时取 `id` 最大者）并 `Updated`，组内其余行全部 `Closed`；
- 交易所已无该 key：整组 `Closed`。

对账前引擎会打 `仓位对账发现重复活跃仓位` 告警（含 id 列表），便于定位被治愈的数据。
远端适配层保证每个 key 只返回一条（CTP 今/昨分片已在适配层按 `(合约,方向)` 聚合），
因此对账内核只处理本地重复，不处理远端重复。

### 2.3 简化流转

```
（不存在）──对账发现交易所有仓──> 持仓中(deleted=false)
持仓中 ──行情写最新价──> 持仓中（重估 roi/max_roi/profit_drawdown 等）
持仓中 ──对账发现交易所已无此仓──> 已平仓(deleted=true, close_time)
已平仓 ──同日对账再发现交易所有仓──> 持仓中（upsert 复活，幂等）
（跨日）──内存 purge──> 历史归档 CSV（不参与内存查询）
```

## 3. 规则状态机

### 3.1 状态集合（`WatchRuleStatus`）

| 状态 | 含义 | 是否终态 |
|---|---|---|
| `active`（默认） | 生效中，每轮引擎扫描都会判定条件 | 否 |
| `pending` | 等待激活（链式规则等待前一条命中后转 active） | 否 |
| `in_use` | 已命中、执行中（平仓单已下发尚未终结）；由引擎占用，外部不可手工置入 | 否 |
| `retired` | 已终止（唯一终态），落状态同时置 `deleted=1` | **是** |

### 3.2 触发状态变化的事件

| 触发源 | 转换 | 说明 |
|---|---|---|
| REST/WS 创建规则 | → `active`（或带 `pending:true` 创建为 `pending`） | |
| 引擎命中「执行自己」 | `active → in_use` | 行锁闭包内 CAS（`claim_self`）：并发触发时只有一个流程成功，杜绝重复下单 |
| 链式命中 | `active → retired` **且** 目标 `pending → active` | `chain_fire` 在同一短临界区内成对完成，前置不符则原样返回、不动任何一行 |
| 关联平仓单到达终态 | `in_use → retired`（+deleted=1） | 统一经 `rules::retire_rule_for_order`：`terminal_rule_id` 判定后校验 account / exchange（规则非空时）/ `rule.created_at <= order.created_at`，通过才 retire；幂等 |
| REST 终态兜底收敛 | `in_use → retired` | WS 漏推时由 `reconcile_terminal_orders` 补收敛；订单被 `force_terminal` 强制收敛后走同一 retire helper |
| 绑定仓位消失 | （active 或 pending 的 risk 规则）→ `retired` | 引擎扫描时发现 position_id 无活跃仓位，直接 retire，不再每轮空判 |
| 绑定仓位账户不匹配 | （active 或 pending 的 risk 规则）→ `retired` | 规则账户可解析且 `position.account_id != rule.account_id` 时按绑定失效 retire；账户未知（尚未热加载）则跳过、保持 active |
| 链式目标跨账户 | 拒绝，当前/目标规则均不变 | `chain_fire` 校验 `current.account_id == target.account_id`，不符返回 `CrossAccount` |
| REST 批量启停 | `retired → active`（`reactivate`，仅终态行可复活）；`active → retired`（手工停用） | `in_use` 不可启停；`pending` 不参与手工启停 |

### 3.3 关键保证

- **`active → in_use` 的 CAS**：只在行写锁闭包内完成，WS 连续推送并发触发时仅一个流程抢到，其余直接跳过；
- **链式激活成对原子**：`chain_fire` 用一把短临界区互斥锁串行化「当前 retire + 目标 arm」两次内存 update，临界区内绝不跨网络/await；
- **retire 幂等**：迟到/重复的终态回报再次触发 retire 时，tombstone 已代表终态，直接成功；
- **retire 归属校验**：订单终态触发的 retire 先校验 account / exchange / created_at，
  防止规则 id 复用后旧订单误杀新规则；
- **仓位绑定账户校验**：`find_position` 只在规则账户可解析时比较 `position.account_id`；
  未知账户保留"跳过、不 retire"语义，避免热加载失败时批量误杀。
- **孤儿回收**：pending 的 risk 后继若绑定仓位已平，主循环扫描前先回收为 retired（否则永远不会再被 arm，且可能被"武装前"的条件为真误触发）。

### 3.4 规则与订单/仓位的联动

```
risk 规则命中
   active ──claim(CAS)──> in_use ──下出规则平仓单（reduce_only，方向由仓位反推）
                              │
                              └──平仓单 FILLED/CANCELED/... 终态（§1）
                                   ──> 规则 in_use → retired(+deleted=1)

链式规则命中
   active ──chain_fire──> retired(+deleted=1)，同时目标 pending → active（回到顶部循环）

仓位被平（任意途径）
   ──> 绑定它的 active/pending risk 规则 → retired（孤儿回收）
```

### 3.5 简化流转

```
                 创建(pending:true)
       ┌────────────────────────────┐
       ▼                            │
  ┌─ active ──命中(self)──> in_use ──平仓单终态──> retired ──reactivate──> active
  │     │                      │                   ▲
  │     │   命中(chain)         │                   │
  │     └──────────────────────┼─── retired ───────┘（当前规则 retire，成对激活目标）
  │                            │
  └──绑定仓位消失──> retired ◀──┘（幂等，tombstone）
```

## 4. 三者软删语义差异（不统一方法的理由）

| 实体 | 终态 | 自动软删？ | 时机 |
|---|---|---|---|
| Order | FILLED/CANCELED/REJECTED/EXPIRED | **是** | 终态落库同一行锁闭包内（`apply_terminal_lifecycle`） |
| Position | closed（deleted=true + close_time） | **是** | 对账裁决 Closed 时 |
| WatchRule | retired | **是** | retire 落状态同时 |

三者终态即 tombstone、当日保留可回查、跨日随内存 purge 进历史归档；但各自的软删触发点与幂等实现不同，故仓储层不强行抽象统一方法。
