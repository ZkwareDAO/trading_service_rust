# 扩展交易所接入指南

> 本文是「如何把一个新交易所接入本系统」的操作手册与踩坑复盘。
> 与 [`交易所适配plan.md`](./交易所适配plan.md) 互补：那篇讲 trait / 结构的设计划分，
> 本篇讲**落地步骤、接线点、以及 Deribit 接入时实际踩到的坑**。
>
> 第一个完整按本框架接入的交易所是 **Deribit（期权）**，可作为后续新所的参照样板。

---

## 一、总体架构（先建立心智模型）

系统对交易所的对接拆成 4 类能力，分属两个对象：

| 能力 | trait | 归属对象 | 说明 |
| --- | --- | --- | --- |
| 下单 / 撤单 / 查单 / 查持仓 / 取参考价 | `ExchangeApi` | **用户主体**（一个「用户 × 交易所」一套凭据） | REST / JSON-RPC，带签名 |
| 账户私有事件流（订单状态 + 仓位脏信号） | `AccountEventStream` | 同上，与 `ExchangeApi` 同对象 | 一条已认证 WS，**不能拆**成两个 trait，否则要开两条连接 |
| 公开行情（价格 / 盘口） | `MarketDataStream`（内部使用） | **交易所主体**（进程内每交易所一个） | 无认证，所有用户共享 |
| 交易规则抓取 | `RuleFetcher` | 交易所主体 | 公开、无认证、全用户共享 |

跨交易所**完全一致**的账户事件消费循环（退避重连、订单→sink、脏信号→去抖→REST 对账、在途防重叠）统一收口在 `trading-exchange/src/account_stream.rs`，新所**不要**再各写一份。

## 二、接入一个新交易所的步骤

以 `crates/trading-exchange/src/<venue>/` 为目录，参照 `deribit/`：

1. **建模块目录**：`<venue>/{mod,pricing,spec,prep,rpc,venue,mapping,market,user_stream,account_consumer,provider}.rs`，并在
   `src/lib.rs` 挂 `pub mod <venue>;`。
   - 不是每个文件都必需，按交易所能力裁剪；现货/合约/期权只实现支持的类型。

2. **定义行情口径映射**：在 `trading-service/src/cashqty.rs` 的 venue→(Venue, MarketKind) 表里加一行，
   保证该所标的能被正确映射到行情键。

3. **标的类型归一化**：如该所引入新的 instrument_type（Deribit 引入了 `option`），
   在 `trading-core/src/protocol.rs::normalize_instrument_type` 加分支。

4. **实现用户主体 `venue.rs`**：
   - 实现 `ExchangeApi`（place/cancel/query/get_positions/reference_price）；
   - 实现 `AccountEventStream`（建连 + 鉴权 + 订阅私有频道）；
   - 鉴权 token 的获取、签名都封装在此，**不泄漏到编排层**。

5. **实现 claim 前预检 `prepare_placement`**（trait `VenueProvider` 的同步、纯内存方法）：
   - 默认实现是原样透传（Binance/demo_venue 不覆盖）；
   - 只有需要「市价转限价 / 平仓价差闸门」的交易所覆盖它。
   - 该方法**只读共享规则表 + 行情表，不做网络 IO**，所以能放在引擎 claim 之前同步调用。

6. **实现私有 WS 运行循环 `user_stream.rs`**：建连、鉴权订阅、读帧、退避重连。
   - 读帧后**逐条**产出事件，交给 `account_stream::run` 消费（见踩坑 1）。

7. **实现账户事件消费适配 `account_consumer.rs`**：
   - 定义本所的 `<Venue>UserProvider` 端口（由 provider 实现）；
   - 一个把本所 user 适配为 `account_stream::AccountUser` 的单元包装；
   - per-account connector 的 `spawn_for` 直接调 `account_stream::run`。

8. **实现公开行情 worker `market.rs`**：
   - 一条恒定主网 WS（不受账户 testnet 影响）；
   - 周期读 `MarketInterest`（持仓 ∪ 规则涉及标的）→ diff 出 subscribe/unsubscribe；
   - ticker 帧字段级写 `QuoteTable`（mark + book），并回调 `QuoteObserver` 驱动仓位重估；
   - 断线清空已订阅集，重连后整体重放。

9. **实现套件 provider `provider.rs`**：`VenueProvider`，提供
   `matches / normalize_instrument / build_api / spawn_account_stream / spawn_market_services`。

10. **登记到注册表**：`trading-exchange/src/registry.rs::builtin` 里 push 一行 provider。
    注册表的路由逻辑与上层 main/service **无需改动**——这是整套设计的核心扩展点。

10.1 **声明仓位流水线档案 `position_profile`**（⚠️ 进行中：随 PositionProfile 改造引入，
    见 [`.claude/plans/position-profile-abstraction.plan.md`](../.claude/plans/position-profile-abstraction.plan.md)）：
    - 在本所 provider 覆盖 `VenueProvider::position_profile()`，自描述一份 `PositionProfile`：
      `exchange / instrument_type（对账作用域）/ quote_venue+quote_kind（on_quote 入站）/ fallback_valuation（快照无价时的估值兜底，None=不兜底）`。
    - 装配由 engine 在 `registry.builtin` 后统一 `load_and_verify` 收口，**不再需要**
      去改 engine 里的 `snapshot_types / quote_target / quote_price` 等共有路径。
    - 若该所持仓端点不返回当前价（如 Hyperliquid 的 `clearinghouseState`），需在自己的
      `get_positions` 内另取价格（HL 用 `allMids`）填入 `PositionInfo.mark_price`，
      避免新仓按 0 价建仓污染 `max_roi`。此为**各所内部处理，不碰共享代码**。

11. **配置**：可调参数（如价差阈值、漂移档数）走 venue 配置文件（`config/venue.toml`），
    在 `trading-service/src/{config,venue_config,state,main}.rs` 接线；文件缺失用内置默认值。

12. **账户配置**：`account.csv` 配置该所账户（api_key / secret / exchange=<venue>），
    凭据经 `CredentialResolver` 解密，禁止硬编码。

## 三、Deribit 接入的关键业务语义

- **市价开仓 → 档位漂移**：不直接吃 mark，而是以 mark 为基准、向有利方向漂移 N 个 tick
  （买低 N tick / 卖高 N tick）挂限价被动单；限价开仓不漂移。
- **市价平仓 → 价差闸门**：
  - `spread <= close_spread_max`：按对手 best bid/ask 转限价平仓；
  - `spread >  close_spread_max`：本轮**不下单、不 claim、不建单**，规则保持 active，
    每轮规则扫描（默认 200ms）重新判价差，收敛后才成交；同时发「需人工平仓」企业微信告警，
    同一 symbol 每 60s 最多发一次。
- **单位 / 结算**：期权按张（`QtyUnit::Contract`），结算币种取合约首段（BTC/ETH）；
  期权无杠杆，`set_leverage` 直接返回"不支持"。

## 四、踩坑复盘（重点，后续接入必读）

> 以下三个问题都在 Deribit 联调时真实遇到，且都**不是编译器或 clippy 能发现的**，
> 属于"接线正确但数据流不通"的运行期问题。

### 坑 1：WS 保活 / 重连——不能"积到断线再一次性推送"

**现象**：私有 WS 的订单回报实时性丢失，订单状态迟迟不更新，直到连接断开才涌进来一批。

**错误做法**：实现账户 WS 时，一度把从交易所收到的订单消息在连接内部**缓存**起来，
打算等 WS 断开后才一次性交给本服务消费。

**问题本质**：
- 账户事件流的价值就在于**逐条、实时**地推进订单状态机；
- 把事件攒在连接缓冲里，等于把"流"退化成"连接结束时的一批快照"，实时性完全丢失；
- 连接可能长时间不断，期间订单状态对系统就是不可见的。

**正确做法（最终实现）**：
- 模仿 Binance 的机制：WS 运行循环读一帧 → **立即**作为 `AccountEvent` 产出 →
  经 `account_stream::run` 实时消费（订单帧 → sink；仓位帧 → 去抖）。
- **保活**：响应交易所 Ping（回 Pong），连接空闲也保持。
- **重连**：连接断开/出错时由 `ReconnectBackoff` 退避（10s/30s/1/3/5min）后立即重建，
  重连成功后**先补发一次全量** `AccountDirty`（拉一次 get_positions），覆盖断线期间的强平/漏单。
- 判据：**事件的生命周期只允许"读到即推"，绝不允许在连接内跨帧积压。**

### 坑 2：REST 下单持续报错——根因是没订阅"代币兴趣集合"

**现象**：测试 REST 下单接口持续失败，下单时拿不到档位价格。

**排查过程**：表面看是下单接口的问题，反复检查下单参数；实际根因在上游行情。

**根因**：
- Deribit 的盘口（best bid/ask）不会无故推送，必须先通过公开行情 WS **订阅对应标的**；
- 行情订阅集合来自 `MarketInterest`（= 活跃持仓 ∪ 规则涉及的条件标的 ∪ 动作标的）；
- 当时没有把标的接进兴趣集合 → 行情 WS 没订阅它 → `QuoteTable` 里没有该标的 bid/ask；
- rule 触发、要做档位漂移/对手价定价时读不到 bid/ask → 下单失败。

**正确做法**：
- 宿主侧 `MarketInterests`（`trading-service/src/interest.rs`）必须正确产出
  「活跃持仓 ∪ 每条未终止规则的条件标的 ∪ 动作标的」；
- 行情 worker 据此动态 subscribe/unsubscribe，ticker 帧写入 `QuoteTable`；
- **下单定价依赖的盘口，前提是该标的已在行情订阅集合内。** 新增交易/规则路径时，
  先确认其标的会进入兴趣集合。
- 判据：**凡是定价要读 bid/ask 的地方，必须保证该 symbol 已被 MarketInterest 覆盖。**

### 坑 3：档位漂移挂单——Deribit 按价格阈值分档，价差取错档导致价格异常

> 适用范围：
> - **下单档位漂移是 Deribit 专属处理，其他交易所没有此机制；**
> - 触发于**市价下单**（经下单 API 提交的市价单：市价单不直接吃盘口，而是漂移成
>   限价被动单）路径；**不是规则平仓**——规则平仓不做档位漂移，主要逻辑是直接取
>   bid/ask（对手价）下单。

**现象**：Deribit **市价下单**（市价单经档位漂移转为限价挂单）时计算出的价格异常，
下单价格不被交易所接受。

**根因**：
- Deribit 标的存在一个**价格阈值**：价格**高于**该阈值时一档（best bid/ask）是
  一种价差，价格**低于**该阈值时一档价差是**另一个值**（价差随价格档位变化）；
- 当时实际价格**低于**该阈值，本应使用低价档对应的一档价差，却没有按当前价格
  所处档位取到正确价差（错用了另一档价差）；
- 用错误价差参与漂移价计算，得出的价格偏离真实 tick、不合法，被交易所拒绝。
- 注意：这不是“没取到一档而落到兜底默认值”的问题——一档数据在，问题在于**没有
  按价格阈值选择对应档位的价差**。

**正确做法**：
- 漂移定价先按当前价格与该标的的**价格阈值**判定所处档位，再取**该档位对应的
  一档价差（best bid/ask）**与合约 tick size 计算漂移价；
- 价格阈值与各档价差、tick size 来自 Deribit 合约规格（`get_instrument` →
  `OrderRule`），盘口来自已订阅的 `QuoteTable`（依赖坑 2：先订阅才有盘口）；
- 取不到真实一档 / 规格、或无法判定价格档位时，**不应用错档或兜底价硬下单**，
  而应返回 `DataNotReady`，让规则保持 active、下轮数据就绪后再定。
- 判据：**价差必须与当前价格所处档位匹配；档位/一档无法确定时宁可不发单
  （DataNotReady），也不用错档或兜底价格冒充。**

### 坑 4：仓位流水线三处硬编码漏配——新增交易所忘改共有路径（Hyperliquid 事件）

> 适用范围：仓位对账/重估接入。2026-09-30 HL 联调时真实遇到；
> 完整修复见 [`.claude/plans/position-profile-abstraction.plan.md`](../.claude/plans/position-profile-abstraction.plan.md)。

**现象**：HL 订单确认 FILLED（交易所侧仓位数量已变），但服务本地仓位表数量/entry
长时间停在旧值，且日志里 HL 每轮对账都是 `created=2 updated=0 closed=0`。

**根因（三处叠加，且都不是编译器/clippy 能发现的运行期数据流问题）**：
- `PositionEngine` 没有复用 `VenueProvider` 的开闭机制，自己硬编码了
  `snapshot_types`（对账作用域产品集）、`quote_target`（on_quote 路由）、`quote_price`（快照估值兜底）三处分派；
- 三处都**漏配 hyperliquid 分支**：
  - `snapshot_types` 对 HL 返回空 Vec → `list_active_scope` 恒空 → 远端持仓每轮都被判 **Created**（反复插新行、旧行不 update/close）→ 表现为"本地表停更"；
  - `quote_target` 丢弃 HL 的 `on_quote` → 仓位不被行情 tick 重估；
  - `quote_price` venue 写死币安 → HL 快照无估值兜底。
- 叠加 HL 特性：`clearinghouseState` **不返回当前价字段**（要价须另调 `allMids`），
  映射又把 `mark_price` 硬编码 None → HL 新仓 Created 时按 0 价，**空单** `revalued(0)`
  算出 roi≈+杠杆并污染 `max_roi`（峰值单调只增、不自愈）。

**正确做法（改造目标）**：
- 把三处硬编码收口为 provider 自描述的 **`PositionProfile`**；engine 在 `builtin` 后
  统一 `load_and_verify`（**装配失败即 fail-fast，拒绝带病启动**）。
  → 以后新增交易所只声明档案 + registry push 一行，**不改 engine 共有路径**。
- 对账 **merge 防御**：REST 快照缺有效价（≤0）时**不得用 0 覆盖本地已有好价**，
  防止"上一秒的好价被这轮无价快照冲掉"。
- 持仓端点不给价的所（HL）：在**自己的** `get_positions` 内补 `allMids` 价，
  让新仓 Created 即带真价——属各所内部实现，不进共享代码。

- 判据：**凡"按交易所分派"的逻辑，都应让该所 provider 自描述，而非在 engine 里
  维护需逐所补全的 match；快照缺价时绝不允许 0 覆盖已有的有效价。**

### 坑 5：跨所条件符号被错挂到动作所——兴趣集并集混入它所标的（Deribit/Hyperliquid 事件）

> 适用范围：跨交易所价格条件。2026-09-30 联调时遇到（deribit 规则条件 `price_BTCUSDT`）；
> 修复收口在服务层 `interest.rs`，**不改各 market worker、不改规则引擎**。

**现象**：deribit market worker 反复对 `instrument="BTCUSDT"` 拉 `public/get_instrument`，
报 `deribit rpc error -32602: Invalid params`，每轮重试、停不下来。

**根因（数据流错挂，编译器/venue 过滤都发现不了）**：
- `interest.rs::collect_rule` 在收集规则兴趣时只按**动作口径**（`r.exchange + r.instrument_type`）
  算一次 venue，然后把**动作标的与条件标的都挂到这同一个动作 venue**；
- 而 `WatchRule.condition_instrument` 只是个符号串、**不携带自己的交易所**。于是
  deribit 规则的跨所条件 `price_BTCUSDT` 被错标成 `(Deribit, Option, "BTCUSDT")`；
- deribit worker 的防御过滤只认 **venue 标签**（`venue==Deribit && kind==Option`），
  该标的已被错标成 Deribit 标签，过滤不掉 → 拿去预热规格 → **-32602 死循环**。
- HL 同理：`(Hyperliquid, Futures, "BTCUSDT")` 也不是 HL 原生形状（HL=裸币 `BTC`）。

**关键澄清（避免误判）**：这**不是「条件缺价」**——Binance 公共行情是全市场全量流
（`!markPrice@arr@1s`，不读兴趣集、无需持仓），`BTCUSDT` 的价一直在 `QuoteTable`；
规则引擎 `market_price` 走 `price_for_symbol` 的**全局按名回退**即可取到，跨所条件能正常判定。
问题只是「错误标的被塞进了 deribit/HL 的订阅/预热集合」。

**正确做法（取完并集后的可复用过滤）**：
- 在 `interest.rs` 兴趣集**并集取完之后**新增一道交易所无关的形状过滤：
  - `is_native_symbol(venue, kind, symbol)`：收口各所符号形状——
    deribit/option 须含 `-`；hyperliquid/futures 为裸币、`USDT` 后缀判异常、`USDC` 宁留勿删；
    **binance 与未知新交易所默认放行**（不了解新所不自动判，防止误删）；
  - `filter_native` / `sanitize_interests`：按 `(venue, kind)` 分组只保留本所形状合法者，
    剔除时记一条 `tracing::debug!` 留痕。deribit/HL 现在通用，未来新交易所只需在
    `is_native_symbol` 登记一条形状规则，过滤机制零改动。
- **铁约束**：只能剔形状异常者，动作标的、本所合法条件标的、仓位标的一个不许误删（有端到端测试钉死）。

- 判据：**兴趣集并集取完后，必须按"该标的形状是否属于本所"过滤；条件符号不携带 venue，
  绝不能默认借用动作所的 venue。默认放行未知所、显式登记形状，才能同时做到可扩展与零误删。**

## 五、接入自检清单

提交一个新交易所前，逐项确认：

- [ ] 私有 WS：订单帧读到即推，无跨帧积压（坑 1）。
- [ ] 心跳保活 + 退避重连 + 重连补全量，已覆盖。
- [ ] 标的已进入 `MarketInterest`，公开行情 WS 确实订阅，`QuoteTable` 有 bid/ask（坑 2）。
- [ ] Deribit 档位漂移：按价格阈值取对档的一档价差与 tick size；档位/一档缺失走 `DataNotReady` 而非错档或兜底价（坑 3；漂移仅 Deribit）。
- [ ] claim 前预检是同步、纯内存，不做网络 IO。
- [ ] 已在本所 provider 声明 `position_profile`，engine `load_and_verify` 通过（档案缺失会 fail-fast）；**未去改 engine 的 `snapshot_types/quote_target/quote_price` 共有路径**（坑 4）。
- [ ] 跨所价格条件：兴趣集并集取完后已按「符号形状是否属于本所」过滤（`is_native_symbol`/`filter_native`），错挂的它所标的不进本所订阅/规格预热（deribit 须含 `-`、HL=裸币；未知所默认放行防误删）；动作/合法条件标的零误删（坑 5）。
- [ ] 持仓端点不给当前价时，已在本所 `get_positions` 内补价（HL=allMids），新仓不按 0 价建仓、不污染 `max_roi`；对账 merge 在快照无价时保留本地好价。
- [ ] 生产代码无 `unwrap/expect`、无 `unsafe`、无硬编码密钥、async 内无阻塞调用。

## 六、Hyperliquid 下单规则字段清单（接入前调研）

> Hyperliquid 的下单规则来自公开接口 `POST /info`，请求体 `{"type":"meta"}`。
> 返回 `universe` 数组，每个币一项，字段形如：
> `{"szDecimals":5,"name":"BTC","maxLeverage":40,"marginTableId":56}`。
> 自己封装下单校验时，**接口实际能拿到 / 拿不到的规则字段如下**，封装应据此对齐，
> 对接口不发布的字段不要硬编码默认值。

### 6.1 可获取的规则字段

| 规则 | 可获取 | 来源 / 推导 | 说明 |
| --- | --- | --- | --- |
| 数量步长 `qty_step` | ✅ | `10^(-szDecimals)` | BTC(szDecimals=5) → 0.00001；下单数量对齐到该步长整数倍 |
| 价格精度 | ✅ | **5 位有效数字**（协议规则/常量，非接口字段） | 高价币少留小数、低价币多留小数；不是固定 tick |
| coin → asset 整数索引 | ✅ | `meta.universe` 数组顺序 | 下单/撤单（asset、cancelByCloid）依赖此索引 |
| 最大杠杆 | ✅ | `maxLeverage` | 可先存入 `OrderRule.extra` |
| 报价 / 结算币种 | ✅ | 恒为 `USDC` | quote_currency 与 settle_currency 均为 USDC |
| 标的是否下架 | ✅ | `isDelisted`（存在即为 true） | 同步规则时过滤下架币 |

### 6.2 不可获取的规则字段

| 规则 | 可获取 | 说明 / 处理 |
| --- | --- | --- |
| 固定价格 tick size | ❌ | HL 无固定 tick，价格口径统一为「5 位有效数字」 |
| 最小数量 `qty_min` | ❌ | `meta` 不发布；本地不校验，交给交易所最终拒绝 |
| 最大数量 `qty_max` | ❌ | 同上 |
| 最小名义额 `notional_min` | ❌ | 接口不发布 |
| 价格区间 `price_min/max` | ❌ | 接口不发布 |

**统一处理原则**：可获取字段在适配器内按 `Decimal` 对齐（数量按 szDecimals 截断、
价格按 5 位有效数字取整、coin/asset 用 meta 缓存索引、未知 coin 本地拒绝）；
接口不发布的字段**不硬编码、不本地校验**，保持「发给交易所、由交易所拒绝兜底」，
收到交易所错误后再映射为明确的拒绝原因。

### 6.3 价格口径分工：mark → 估值/条件，mid → IOC 定价

> Hyperliquid 的 `mid`（allMids）与 `mark`（activeAssetCtx.markPx）并不一致：
> 剧烈单边行情里 mark 因混合 EMA/外部 CEX 价格而滞后于 mid；HL 相对外部市场
> 持续升贴水时二者也有稳定差距。二者在本系统里服务**不同消费方**，**不互相替换**：

| 口径 | 用途 | 读取方式 |
| --- | --- | --- |
| **mark** | **估值（直接）/ 规则条件（多为间接）**：仓位重估写 current_price/PnL/ROI、现金换算数量（无盘口时） | `valuation_price()`（mark>mid>last） |
| **mid** | **Hyperliquid 市价 IOC 定价**：市价开仓与市价平仓的 IOC 限价基准（mid±slippage） | venue `place_order` 内部读取 |

mark 对各类规则条件的作用路径（区分直接 / 间接）：

| 规则条件 | 判定时读取 | mark 作用 |
| --- | --- | --- |
| 本仓 ROI / ProfitDrawdown | 内存 `position.roi` / `profit_drawdown` | **间接**（上游仓位重估写 position） |
| 本仓 Price | 内存 `position.current_price` | **间接**（同上） |
| 跨标的 Price（condition_instrument 指向其它标的） | `price_of(symbol)` 直接查行情表 | **直接** |
| Position（持仓量） | 仓位数量，与价格无关 | 不涉及 |

要点：
- 规则判定**不实时计算 ROI**，读的是 position 已重估字段；mark 经"仓位重估用什么价"
  间接影响本仓条件，仅跨标的 Price 条件直接读 mark。
- 因此只要保证仓位重估用 mark（缺失回退 mid），本仓条件自动是正确口径，规则侧无需单独订 mark。
- mark 与币安合约、HL 自己的清算/止盈止损触发同口径；其「滞后」在风控视角是优点。
- 市价 IOC 要去吃**真实订单簿**，快速行情里 mark 滞后会影响成交，故 IOC 基准用 mid。
- **平仓下单不用 mark 定价**：市价平仓走 mid 的 IOC、限价平仓走规则配置价；mark 只
  决定「仓位值多少钱、规则要不要触发」。
- 订阅拓扑：`allMids`（全量、常开）写 `Quote.mid`；`activeAssetCtx`（仅订阅
  兴趣集内的币）写 `Quote.mark`。
- activeAssetCtx 报文必带一个 EVM 地址，但服务端不校验该地址身份、无需私钥或持币；
  markPx 属币级公开数据、与传入哪个地址无关（已实测零地址即可）。故实现用**全零
  地址**（`market.rs::CTX_ROUTE_USER`）作「无特定 user」的中性占位，不依赖任何
  真实/第三方地址，也无需为此透传账户清单。

### 6.4 接入要点与踩坑（hyperliquid）

- **凭证口径与币安不同**：`account.csv` 里 `exchange=hyperliquid`，签名只认
  `api_secret`（EVM 私钥，hex，建议 `enc.v1` 加密）；`api_key` 仅作地址记录、
  不参与签名，`api_passphrase` / `position_mode` 不用。
- **connectionId 用 MessagePack，不是 JSON**：L1 action 经
  `rmp_serde::to_vec_named`（带字段名的 map）序列化，再追加 8 字节大端 nonce 与
  1 字节 vault 标志后 Keccak256；发给交易所的 body 才是 JSON。两者不要混。
- **EIP-712 domain 固定**：name="Exchange"/version="1"/chainId=1337；`source`
  主网="a"、测试网="b"，签名前按 `is_testnet` 选。
- **签名分片**：exchange 请求体的 `signature` 是 `{r,s,v}` 对象（r/s 为 0x+32
  字节、v=27/28），不是一整串 hex。
- **无真市价单**：市价一律转 `tif=Ioc` 的限价，价格=mid×(1±slippage，默认5%)，
  数量按 `10^-szDecimals` 对齐；交易所不发布 min_qty / 固定 tick，缺这些不本地造。
- **asset 索引以下架币占位**：即使某币 `isDelisted`，universe 索引仍按原始顺序
  计数（只是不生成规则行），保证在线币索引与交易所一致。
